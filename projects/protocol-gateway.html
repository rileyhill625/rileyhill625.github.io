Protection & Control Complete

Substation Protocol Gateway

The communication layer that ties a substation together — a Modbus TCP relay server, a SCADA monitor that polls it and applies protection logic, and a study of the three protocols a real substation runs on. Built from the ground up in Python, not configured through a vendor tool.

Objective

A large part of P&C and SCADA integration is getting field devices to talk to control systems — mapping a relay's data into a SCADA master and troubleshooting the link when it breaks. That work is far easier when you understand the protocol mechanics directly instead of treating a vendor's mapping tool as a black box.

This project builds a complete Modbus TCP system from scratch — a server that acts as a relay, a monitor that acts as the control room — so the underlying mechanics (registers, coils, scaling, addressing, polling versus events) are understood first-hand. A written study then extends that into DNP3 and IEC 61850 GOOSE, the other protocols a working substation depends on.

Architecture

A simulated relay serves live telemetry over Modbus TCP; a SCADA monitor polls it once a second and applies protection logic; a simulator writes changing values so the system behaves like a live feed. The same relay data is designed to flow onward to an Ignition HMI over OPC.

The data model

Modbus stores data in typed slots — coils for single on/off bits, holding registers for 16-bit whole numbers. Since registers can't hold decimals, current is scaled by ten (39.5 A stored as 395 and divided back on read). The relay exposes three values:

AddressTypeHoldsEncoding
Register 1Holding registerCurrentAmps ×10 (395 → 39.5 A)
Register 2Holding registerVoltageVolts (12470)
Coil 1CoilBreaker status1 = closed, 0 = open (tripped)

A detail that trips up everyone new to Modbus: the client addresses these 0-based while the server stores them starting at 1 — the classic Modbus off-by-one. Handling that correctly is exactly the kind of real-world quirk this project exists to internalize.

The SCADA monitor

The monitor is the control-room side: it polls the relay every second, classifies each reading against a pickup threshold, and — crucially — logs state changes as events rather than spamming every identical poll. That poll-then-classify-then-log-events pattern is the heart of what a real SCADA master does.

03_scada_monitor.py — polling + protection logic Full code ↗ 
PICKUP_A = 55.0   # pickup above load, below minimum fault — the protection window

while True:                                    # a real monitor never stops
    rr = await client.read_holding_registers(address=0, count=2)
    rc = await client.read_coils(address=0, count=1)
    current = rr.registers[0] / 10.0           # undo the x10 register scaling
    breaker_closed = rc.bits[0]

    if not breaker_closed:
        status = "*** ALARM: BREAKER OPEN (relay tripped) ***"
    elif current > PICKUP_A:
        status = f"!! WARNING: overcurrent {current} A > pickup {PICKUP_A} A"
    else:
        status = f"OK  current={current} A"

    # log CHANGES as events — not every identical poll
    if last_breaker is not None and breaker_closed != last_breaker:
        print(f">> EVENT: breaker -> {'CLOSED' if breaker_closed else 'OPEN'}")
    last_breaker = breaker_closed
    print(status)
    await asyncio.sleep(1)                      # poll every second

Protocol comparison

Modbus is one of three protocols a real substation relies on, each suited to a different job. The written study compares them; the essentials:

ProtocolModelTimestamping / SOESpeedTypical use
ModbusPolling — master asksNone (poll snapshots)ModerateSimple device telemetry
DNP3Event-driven reportingYes — sequence-of-eventsEfficient over WANWide-area utility SCADA
IEC 61850 GOOSEPublish/subscribe, Layer 2Event-drivenVery fast (< 4 ms)Protection signaling between IEDs

The key distinction: DNP3's advantage over Modbus isn't raw speed — it's event capture. DNP3 timestamps changes and reports them unsolicited, so a control center gets an ordered sequence-of-events (what happened, and exactly when), where Modbus only ever returns a snapshot of the moment it was polled. GOOSE is a different animal entirely: fast Layer-2 peer-to-peer messaging for protection devices to trip each other in milliseconds.

Note: DNP3 and GOOSE are documented conceptually rather than implemented, because in practice they're deployed through C++ stacks (OpenDNP3, libiec61850) or vendor tools — the maintained Python libraries are limited or unmaintained. Building Modbus fully in code and studying the other two as they're actually deployed is the honest, useful split.

Ties to the portfolio

The relay this gateway simulates is the software mirror of the hardware IDMT relay, and the pickup threshold in the monitor follows the same above-load / below-fault logic staged across devices in the feeder coordination study. The live data it serves is what the Ignition SCADA dashboard consumes over OPC — connecting field device, protocol, and control room into one working system.
